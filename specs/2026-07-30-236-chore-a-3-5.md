# Issue #236 — Remove the committed `fake-agent` binary and guard against the next one

## Problem

`fake-agent` — a 3,519,314-byte Mach-O 64-bit arm64 executable — was committed
at the repository root on `main`. It arrived with
`refactor(provider): remove Forgejo and Tea support` (e945c0e, #161) and became
the largest file in the repository, ahead of the architecture diagram.

Three separate problems:

1. **It is a build artifact, not source.** `internal/e2e/harness/fake_agent.go`
   is the real thing; the committed file is a compiled copy that someone built
   and `git add`-ed. Nothing in the build or test path references the binary.
2. **It is architecture-specific.** An arm64 Mach-O is useless on the Linux
   runners CI actually uses, so it cannot even be the reason it was committed.
3. **It is permanent.** Deleting it from `HEAD` leaves it in history; every
   clone still pays for it forever unless history is rewritten.

The interesting question is not the file, it is that nothing stopped it.
`.gitignore` had no entry that would have caught it, and no pre-commit hook or
CI check rejected large or executable files. `AGENTS.md` already states "Build
output lives in `dist/`; do not edit generated files" — that convention existed
and was not enforced.

## Goals

- Remove `fake-agent` from `HEAD`.
- Make `.gitignore` cover build output at the repository root, including bare
  executables produced by `go build` without `-o`.
- Add a check — CI step, and optionally a pre-commit hook — that rejects newly
  added binary or executable files above a stated size threshold, with a
  documented escape hatch for intentional assets like `assets/*.png`.
- Prove the check by a test or a deliberate trial run, not just an assertion.

## Non-goals

- Rewriting history to purge the blob. 3.5 MB does not justify it; the point is
  to stop the next one, not to retroactively shrink the pack.
- Addressing the 555 KB `internal/reviewer/runner_test.go` noted in the issue.
  That is a separate "explosive test-file growth" design smell flagged in
  `AGENTS.md` and warrants its own investigation.

## Approach

### 1. Remove the binary from HEAD

`git rm fake-agent` and commit. The blob remains in history; that is accepted
per the non-goals.

### 2. Extend `.gitignore` for root-level build output

`go build` without `-o` drops a bare executable named after the package's main
import at the repository root. Add explicit ignore entries for the binaries the
build and e2e harness produce there:

- `/looper`, `/looperd`, `/loopernet` — the supported entrypoints.
- `/fake-agent`, `/fake-gh`, `/fake-osascript` — the e2e harness commands.

Anchored (`/`-prefixed) entries match only at the root, so a same-named file
under a subdirectory is not silently swallowed.

### 3. A CI check that rejects committed artifacts

Add `tools/check-binaries`, a small Go program run from the repository root that:

- Lists tracked files via `git ls-files`.
- For each file not on an explicit allowlist, reads the first four bytes and
  checks for an executable-binary magic: Mach-O (thin and fat, both
  endiannesses), ELF, and PE (`MZ`).
- Independently of magic, flags any tracked file exceeding a size threshold
  (1 MiB — the largest legitimate source file is well under this).
- Allowlists intentional large/binary assets by path prefix: `assets/`,
  `.codex/reports/`, and `web/dashboard/pnpm-lock.yaml`.
- Exits non-zero with one message per violation and a hint pointing at `dist/`
  and the allowlist.

Wire it into `.github/workflows/ci.yml` in the `verify` job, after `Lint`
(`go vet ./...`) and before `Test`. It runs on every PR update alongside the
existing gates, so a committed binary fails CI rather than landing on `main`.

### 4. Prove it by test, not assertion

A unit test (`tools/check-binaries/check_test.go`) fabricates the offending
shapes against an in-memory `fstest.MapFS`:

- Mach-O, PE, and ELF magic-prefixed files → rejected.
- An oversized file (`maxTrackedFileBytes + 1`) → rejected.
- Allowlisted assets of the same oversized size (`assets/diagram.png`,
  `web/dashboard/pnpm-lock.yaml`) → accepted.
- Ordinary source (`main.go`) and a shell script (`scripts/run.sh`) → accepted.

The test asserts exactly the four artifacts are rejected and the four
legitimate files pass, pinning both the classifier and the allowlist. A second
test pins the `maxTrackedFileBytes` constant so the threshold changes
deliberately, in lockstep with the allowlist, rather than by drift.

CI running `go run ./tools/check-binaries` on HEAD is the trial run: the tree
is clean, so the check exits green, proving it does not false-positive on the
real repository.

## Design trade-offs

> Delete this six months from now — what breaks?

The next `go build`-without-`-o` whose output someone `git add`s fails CI
instead of landing. That is the concrete failure being prevented. A simpler
move — relying on the `AGENTS.md` "build output lives in `dist/`" convention —
already existed and was not enforced; the check is the enforcement.

> What does it still not catch?

- Files under 1 MiB with no executable magic (e.g. a committed `.zip` or
  `.tar`) pass. The threshold targets the observed failure shape (a large
  binary), not arbitrary blobs.
- A binary committed under an allowlisted prefix (e.g. `assets/evil`) would
  pass. The allowlist is path-prefix based and intentionally narrow; widening
  it is a deliberate act.
- It runs in CI, not as a pre-commit hook, so a contributor can still stage the
  file locally — they just cannot merge it. A pre-commit hook is optional and
  not added here to avoid imposing tooling on every contributor's local
  environment.

### Authority

The authority for the rejection is the file's own bytes (magic number) and
size on disk, read from the working tree via `git ls-files` — not agent output
and not an inference over build state. The allowlist is the only judgment call,
and it is an explicit, reviewed list of path prefixes.

## Risks

- **False positives on legitimate large assets.** Mitigated by the explicit
  allowlist; the test pins both the rejected and the accepted set so a
  regression in either direction is caught.
- **Threshold drift.** The 1 MiB constant is pinned by a test; raising it
  requires a deliberate change alongside the allowlist.
- **Allowlist rot.** A prefix that no longer corresponds to a real asset
  directory silently widens the hole. The allowlist is small and reviewed in
  the same diff as any new asset; no automatic sync check is added because the
  cost of keeping one in sync would exceed the cost of the rot it prevents for
  a three-entry list.
- **CI-only enforcement.** A binary can be committed locally; it just cannot
  merge. Accepted: CI is the single chokepoint every change already passes
  through.

## Validation

- `go test ./tools/check-binaries/...` — the fabricated-shapes test passes,
  rejecting exactly the four artifacts and accepting the allowlisted/source
  files.
- `go run ./tools/check-binaries` on a clean HEAD exits 0 — the trial run
  proving no false positive on the real tree.
- `go build ./...`, `go vet ./...`, `go test ./...` remain green.
- CI `verify` job runs the new "Reject committed binaries" step after Lint and
  before Test.
- `git ls-files | grep fake-agent` returns nothing after the removal commit.

## Files

- `fake-agent` — removed.
- `.gitignore` — add root-level executable entries (`/loopernet`, `/fake-agent`,
  `/fake-gh`, `/fake-osascript`; `/looper` and `/looperd` already present).
- `tools/check-binaries/main.go` — `git ls-files` driver, exits non-zero on
  violations.
- `tools/check-binaries/check.go` — magic-number + size classifier with
  allowlist.
- `tools/check-binaries/check_test.go` — fabricated-shapes proof.
- `.github/workflows/ci.yml` — new "Reject committed binaries" step in `verify`.
