# Spec: One typed mergeability-state model shared by Gatekeeper and mergewatch (#467)

- **Issue:** MumuTW/looper#467 — refactor(github): one typed mergeability-state model shared by Gatekeeper and mergewatch
- **Base branch:** `main`
- **Type:** Refactor of the GitHub mergeability-state boundary; consumer dispatch unchanged (one deliberate durable-snapshot field-source fix, documented in section 2)
- **Lifecycle:** This spec PR *references* #467; it must **not** close it. The diff is planning-only — no typed boundary, consumer migration, or regression tests land here — so #467 stays open until the implementation PR lands. The PR body must use a non-closing reference (e.g. `Refs #467`), not `Closes #467`, or GitHub will auto-close the implementation issue the moment this spec reaches the default branch.
- **Refs:** #386 (consolidating shared role types across packages — same spirit of moving a hand-rolled vocabulary into one typed boundary). No open issue today adds mergeability-state-keyed consumer logic; the consolidation is grounded in the two existing copies (Gatekeeper + mergewatch), not in a speculative third/fourth consumer.

## Problem

GitHub's mergeability vocabulary reaches the daemon as a raw string and is pattern-matched independently in two packages, against two hand-rolled subsets of the same undocumented magic strings (`"clean"`, `"dirty"`, `"blocked"`, `"unstable"`, `"has_hooks"`, `"unknown"`, plus the GraphQL-only `"behind"`).

- **Gatekeeper** (`internal/gatekeeper/runner.go:336-347`): lowercases + trimming at the consumer, then `"dirty"` → `ReasonMergeConflict`; `providerPolicyStateIsAmbiguous` (`runner.go:643-650`: `"blocked"`, `"unstable"`, `"has_hooks"`) → `ReasonProviderStateAmbiguous`; anything else non-`"clean"` → `ReasonMergeabilityNotClean`. The `Mergeable == nil || state == "" || state == "unknown"` branch (`:338`) is a separate ambiguity path.
- **Coordinator mergewatch** (`internal/coordinator/mergewatch/mergewatch.go:90,102` and `internal/coordinator/mergewatch_runner.go:184-219`): lowercases + trimming at the consumer (`mergewatch_runner.go:184`), then compares against `"unknown"` (`:90`), `"dirty"` (`:102`), and `"unstable"` (`:205,216`) with its own action mapping. `Classify` (`mergewatch.go:73`) receives the already-normalized string on `PRSnapshot.MergeableState`.

Two packages, two normalizations, two subsets, no shared source of truth. The concrete failure is those two copies already diverging in their subsets and normalization; any future logic that branches on mergeability state would re-derive the vocabulary a third time. Divergence here is exactly the class of bug the compiler should catch — the invariant belongs in a type, not in each consumer's memory of GitHub's vocabulary. The raw string also leaks through two transport shapes: the REST `mergeable_state` field (lowercase) and the GraphQL `mergeStateStatus` field (uppercase: `CLEAN`, `DIRTY`, `BLOCKED`, `UNSTABLE`, `HAS_HOOKS`, `UNKNOWN`, `BEHIND`). The gateway already collapses these at `gateway.go:1731` (`firstNonEmpty(mergeable_state, mergeStateStatus)`), so a consumer can receive either casing; today each consumer re-lowercases to defend against that.

## Goals

- A typed `MergeabilityState` in the GitHub infra layer (`internal/infra/github`), parsed **once at the gateway boundary** from the raw string, with three distinct "we don't know" cases that preserve the original string as evidence: `Empty` (the absent/empty `""`), `Unknown` (the explicit `"unknown"`), and `Unrecognized` (any non-empty, non-`"unknown"` value not in the known set — a genuinely unseen provider value such as a future `"pending"`). The GraphQL-only `"behind"` and GitHub's existing `"draft"` are **not** `Unrecognized`: they are routine, documented provider values for ordinary PR states (behind base, draft), so they get their own recognized fall-through kinds `Behind` and `Draft` (no consumer predicate besides `!IsClean()`, `IsUnrecognized()` false) — this is what keeps the section 2 unrecognized-state diagnostic from firing on every gateway read of a behind/draft PR. `Empty` and `Unknown` are separate kinds because Gatekeeper treats both as provider-ambiguous while mergewatch treats only `"unknown"` as indeterminate and lets `""` fall through. The zero value of the type is `Empty` so uninitialized values fail closed (not clean) without being misread as the explicit provider-`unknown`.
- Semantic predicates on the type — `IsClean()`, `HasConflict()`, `IsAmbiguousPolicyState()`, `IsEmpty()`, `IsUnknown()`, `IsUnstable()`, `IsUnrecognized()` — so consumers and the gateway state intent instead of comparing strings. The predicate set is the *union* of what Gatekeeper, mergewatch, and the gateway diagnostic currently ask, no more: Gatekeeper asks "empty **or** unknown" (`IsEmpty() || IsUnknown()`), mergewatch asks "unknown only" (`IsUnknown()`), the gateway asks "unrecognized only" (`IsUnrecognized()`). `Empty`, `Behind`, `Draft`, and `Unrecognized` deliberately match no consumer predicate besides `!IsClean()` (and `IsEmpty()` for `Empty`), preserving today's fall-through; `Unrecognized` additionally matches `IsUnrecognized()` for the diagnostic only, and `Behind`/`Draft` deliberately do **not** match `IsUnrecognized()` so the diagnostic stays silent for those ordinary states.
- Gatekeeper and mergewatch consume the type; the raw string survives only inside in-memory telemetry/audit. Durable `Evidence` persists the parser's `Normalized()` form so existing eventlog readers see byte-identical values. The type also implements `json.Marshaler`/`Unmarshaler` (emitting/accepting `Normalized()`) so any struct that embeds it — notably `PullRequestDetail` marshaled into `CapturePullRequestSnapshot`'s durable `PayloadJSON` — persists the same JSON string, not `"MergeableState":{}`.
- Exhaustive switch coverage in the parser so a newly observed provider state is captured in one place (as `Unrecognized`, auditable via `Raw()`) instead of silently falling through two consumers; an explicit exhaustiveness test (not compiler enforcement) keeps the kind set and predicates in sync.
- Behavior unchanged: the existing Gatekeeper reason mapping and mergewatch action mapping are preserved exactly, covered by regression tests against the shared type.

## Non-goals

- Changing *what* each consumer does with a given state. The reason/action mapping tables stay as-is; only the dispatch mechanism (string compare → typed predicate) changes.
- Touching the GraphQL `mergeStateStatus` → `HasConflicts` probe (`gateway.go:803,839,1680`). That is a separate boolean derived from `DIRTY` for discovery-list fast paths and is not part of the mergeability-state consumer surface this issue targets. It is noted only because the typed parser must accept the uppercase GraphQL vocabulary too.
- Adding new consumer predicates or new gates. This is a consolidation, not an expansion. The only new kinds are the recognized fall-through kinds `Behind` and `Draft` (section 1), which carry no consumer predicate besides `!IsClean()` and exist solely to keep the unrecognized-state diagnostic honest; they add no consumer-facing state, predicate, or gate. Any future consumer that needs to branch on a mergeability state extends this type instead of adding a third string-compare site; this refactor only gives that extension one place to land.
- Persisting the typed enum in `Evidence`/eventlog. The durable `Evidence.MergeableState` field stays a string for backward-compatible audit reads; the type is a dispatch boundary, not a new persisted concept. It does cross one persisted-struct boundary — `PullRequestDetail` marshaled into `CapturePullRequestSnapshot`'s `PayloadJSON` — but only as a JSON string via `MarshalJSON`/`Normalized()`, so no new persisted shape or field is introduced (see section 1, JSON transport). The *value* stored there does change for the GraphQL view path, because the field-source fix in section 2 corrects a latent always-empty read; that durable-data change is documented and tested in section 2, and is the one intentional non-byte-identical effect of this refactor.

## Authority

> **What is the authority for this action, and why is it not the agent's own structured output?**

This refactor adds no gate, validation, or persisted field — it moves an existing string-to-decision mapping into a type. The authority for "what does state X mean" is GitHub's documented `mergeable_state` / `mergeStateStatus` vocabulary, parsed once at the gateway where the raw provider response enters the process. Consumers stop re-deriving that meaning locally. There is no agent output in this path, so the agent-output trust question does not arise.

## Trade-off

> Delete this six months from now — what breaks?

The two consumers revert to independent `strings.ToLower(strings.TrimSpace(...))` + hand-rolled string subsets. Any future logic that branches on mergeability state then lands as a third copy of the same vocabulary with no shared source of truth, and the silent divergence the type prevents returns: one consumer can recognize `behind`/`draft`/`has_hooks` while the other does not, with no compile or test signal. The regression tables pinned against the shared type (every state both consumers handle, mapped to its reason/action) lose their meaning, because there is no longer one type to pin them against.

> What does it still not catch?

It types only the values GitHub returns today. A genuinely new provider value still lands in `MergeabilityUnrecognized` and falls through to the existing `ReasonMergeabilityNotClean` / check-pending behavior — the type makes it auditable (`Raw()` preserved) and exhaustively tested, but does not by itself decide what the new value *means*. It also does not catch predicate *misuse* (a consumer calling the wrong predicate for its intent); it catches only string-vocabulary divergence and the "two normalizations" drift. Finally, it does not catch a consumer that re-introduces a local string compare alongside the predicates — the "no string literals remain" grep in Validation is the backstop for that, not the type.

> Why deletion or failing loudly is insufficient.

Deleting the type does not surface the divergence — it just hides it again in two consumers' memories. Failing loudly on every unrecognized value (mapping it to `IsUnknown()` and the provider-ambiguity path) was the first draft and is rejected here: it changes behavior for the unrecognized + non-nil `Mergeable` case, which today falls through to `ReasonMergeabilityNotClean` (Gatekeeper) and normal check/pending (mergewatch). The type's value is consolidating the *known* vocabulary in one exhaustively-tested place while preserving the existing fall-through for what it does not know — neither deletion nor fail-loud gives both properties.

## Approach

### 1. The type — `internal/infra/github/mergeability.go`

A new small file in the existing `internal/infra/github` package (no new package — the gateway already lives here and is the parse site).

```go
type MergeabilityState struct {
    kind  MergeabilityKind
    raw   string // original string, preserved for evidence/telemetry
}

type MergeabilityKind int

const (
    // MergeabilityEmpty is the zero value so an uninitialized
    // MergeabilityState{} fails closed (IsClean() == false) instead of
    // reporting clean. It covers the absent/empty mergeable_state input,
    // which the REST/GraphQL decoders produce independently of the
    // mergeable boolean (a missing/null field decodes to "" regardless of
    // mergeable). It is distinct from Unknown so mergewatch can preserve
    // its existing empty-state fall-through (see section 4).
    MergeabilityEmpty MergeabilityKind = iota
    MergeabilityUnknown      // explicit provider-"unknown": GitHub has not computed a value
    MergeabilityClean        // clean, mergeable
    MergeabilityDirty        // conflict
    MergeabilityBlocked      // policy blocker, ambiguous
    MergeabilityUnstable     // failing/pending required checks, ambiguous
    MergeabilityHasHooks     // server-side hooks pending, ambiguous
    MergeabilityBehind       // GraphQL BEHIND / REST "behind": PR is behind its base — known fall-through
    MergeabilityDraft        // GraphQL DRAFT: draft PR — known fall-through
    MergeabilityUnrecognized // a genuinely unseen non-empty, non-"unknown" value not in the known set
    // mergeabilityKindCount is a sentinel that bounds the enum range; it
    // must remain the last constant. The exhaustiveness test iterates
    // [MergeabilityEmpty, mergeabilityKindCount) mechanically (see section
    // 5), so inserting a new kind above this sentinel automatically
    // extends the iterated range — there is no hand-maintained kind slice
    // to forget to update.
    mergeabilityKindCount
)
```

Three distinct "we don't know" kinds, with different semantics, so the refactor preserves today's behavior exactly. The empty string and the explicit `"unknown"` are **separate kinds** because the two consumers treat them differently today: Gatekeeper treats both `""` and `"unknown"` as provider-ambiguous (`ReasonProviderStateAmbiguous`), while mergewatch treats only `"unknown"` as indeterminate and lets `""` fall through to its normal check/pending classification. Folding them into one kind (and one `IsUnknown()`) would change mergewatch for the empty + non-nil `Mergeable` case — the REST/GraphQL decoders produce an empty `mergeable_state` independently of `mergeable`, so that case is reachable, not hypothetical. Keeping them distinct is what lets each consumer express its actual intent:

- `MergeabilityEmpty` — the absent/empty `mergeable_state` input (`""`). `IsEmpty()` is true; `IsUnknown()` is false. Gatekeeper routes it to `ReasonProviderStateAmbiguous` (today's `state == ""` arm). mergewatch does **not** route it to indeterminate — with a non-nil `Mergeable` it falls through to the normal check/pending classification, exactly as today's `snapshot.MergeableState == "unknown"` check (which does not match `""`) produces. It is the zero value so an uninitialized `MergeabilityState{}` fails closed (`IsClean() == false`) without being misread as the explicit provider-`unknown`.
- `MergeabilityUnknown` — the explicit provider-`"unknown"` value. `IsUnknown()` is true. This is the only kind that drives Gatekeeper's `ReasonProviderStateAmbiguous` early block (together with `Empty` and nil `Mergeable`) **and** mergewatch's indeterminate/deadline path. (The `Mergeable == nil` check stays separate at the consumers, exactly as today.)
- `MergeabilityUnrecognized` — a genuinely unseen non-empty, non-`"unknown"` string the parser does not recognize (e.g. a future `"pending"`). It preserves the original string via `Raw()` but **keeps the existing fall-through behavior**: not clean, not conflict, not ambiguous-policy, not empty, not unknown, so Gatekeeper routes it to `ReasonMergeabilityNotClean` and mergewatch routes it to its normal check/pending classification — the same outcome today's code produces for any unmatched string with a non-nil `Mergeable`. Mapping it to `IsUnknown()` instead would be a behavior change (Gatekeeper provider block + mergewatch indeterminate) and is deliberately not done. This is the **only** kind for which `IsUnrecognized()` is true, so the section 2 unrecognized-state diagnostic fires only for a value GitHub has never returned before — not for the routine `behind`/`draft` states, which have their own kinds below.
- `MergeabilityBehind` and `MergeabilityDraft` — recognized fall-through kinds for the GraphQL `BEHIND` / REST `"behind"` and GraphQL `DRAFT` values. These are routine, documented provider states for ordinary PRs (behind base, draft), **not** unseen vocabulary, so they are **not** `MergeabilityUnrecognized` and `IsUnrecognized()` is false for them. They carry no consumer predicate besides `!IsClean()` (not clean, not conflict, not ambiguous-policy, not empty, not unknown, not unstable), so Gatekeeper routes them to `ReasonMergeabilityNotClean` and mergewatch routes them to its normal check/pending classification — byte-identical to today's fall-through, where both values already produce exactly those outcomes. `Raw()` retains the original string for audit. The reason these are named kinds rather than collapsed into `Unrecognized` is the section 2 diagnostic: if `behind`/`draft` shared `Unrecognized`, then `IsUnrecognized()` would be true for them and the unrecognized-state warning would fire on every gateway read of a behind/draft PR (PR views and mergewatch polling hit these paths repeatedly, with no deduplication), writing misleading warning entries that suggest new vocabulary was observed when it was not. Giving them their own fall-through kinds makes `IsUnrecognized()` mean exactly "genuinely unseen," so the diagnostic stays honest. Adding a *consumer predicate* for `Behind`/`Draft` (e.g. `IsBehind()`) is deferred until a consumer actually needs to branch on either; the kind itself is added now because the diagnostic already needs to distinguish them.

- `ParseMergeabilityState(raw string) MergeabilityState` is the single parse site. It trims, lowercases, and switches exhaustively over the known vocabulary (`""` → `Empty`; `"unknown"` → `Unknown`; `"clean"` → `Clean`; `"dirty"` → `Dirty`; `"blocked"` → `Blocked`; `"unstable"` → `Unstable`; `"has_hooks"` → `HasHooks`; `"behind"` → `Behind`; `"draft"` → `Draft`). The `default` arm sets `MergeabilityUnrecognized` and keeps the original `raw` so a genuinely unseen provider value is auditable and falls through with the old behavior, not silently re-classified as provider-ambiguous. `"behind"` and `"draft"` are explicit cases (not `default`) precisely so they do **not** land in `Unrecognized` and the section 2 diagnostic does not fire for them; their kinds carry no consumer predicate besides `!IsClean()`, so the dispatch outcome is byte-identical to today's fall-through while `Raw()` retains the original string for audit (see the `MergeabilityBehind`/`MergeabilityDraft` kinds above).
- Predicates: `IsClean()`, `HasConflict()`, `IsAmbiguousPolicyState()` (true for `Blocked`/`Unstable`/`HasHooks` — the existing `providerPolicyStateIsAmbiguous` set), `IsEmpty()` (true *only* for `Empty`), `IsUnknown()` (true *only* for `Unknown` — the explicit `"unknown"`, not the empty string), `IsUnstable()` (true only for `Unstable`; the one consumer-specific kind predicate mergewatch needs), `IsUnrecognized()` (true *only* for `Unrecognized` — the diagnostic predicate the gateway parse call sites invoke at section 2 to decide whether to emit the unrecognized-state warning), `Raw() string` (returns the preserved original string for telemetry/audit), `Normalized() string` (returns `strings.ToLower(strings.TrimSpace(raw))` — the byte-identical representation today's consumers persist, used for durable evidence and reason subjects). The predicate set is the union of what Gatekeeper and mergewatch currently ask plus the one diagnostic predicate the gateway itself needs: Gatekeeper asks "empty **or** unknown" (so it uses `IsEmpty() || IsUnknown()`), mergewatch asks "unknown only" (so it uses `IsUnknown()`), and the gateway asks "unrecognized only" (so it uses `IsUnrecognized()`). `Empty`, `Behind`, `Draft`, and `Unrecognized` match no consumer predicate besides `!IsClean()` (and `IsEmpty()` for `Empty`), preserving today's fall-through; `Unrecognized` additionally matches `IsUnrecognized()` for the diagnostic only, and `Behind`/`Draft` deliberately do **not** match `IsUnrecognized()` so the diagnostic stays silent for those ordinary states — neither alters any consumer's dispatch.
- **JSON transport:** `MergeabilityState` implements `json.Marshaler` and `json.Unmarshaler`. `MarshalJSON` emits `Normalized()` as a JSON string (e.g. `"clean"`, `""`); `UnmarshalJSON` accepts a JSON string and routes it through `ParseMergeabilityState`. This is required because `CapturePullRequestSnapshot` (`gateway.go:3170`) marshals the entire `PullRequestDetail` into durable `PayloadJSON` (`payloadMap := map[string]any{"detail": detail, ...}` at `:3189`, persisted at `:3217`). Both struct fields (`kind`, `raw`) are unexported, so without an explicit `MarshalJSON` the default `encoding/json` behavior would emit `"MergeableState":{}` and discard the provider state — breaking the stored snapshot schema outside the `Evidence`/eventlog boundary the spec otherwise controls. `MarshalJSON` returning `Normalized()` keeps `PayloadJSON` a JSON string in the same byte-identical normalized form used for `Evidence`, so the type is safe to embed in any persisted struct, not just in-memory telemetry.
- `Behind`/`Draft` are named kinds with **no consumer predicate** besides `!IsClean()`: Gatekeeper currently routes `behind` and `draft` to `ReasonMergeabilityNotClean` (the "not clean, not ambiguous, not conflict" fall-through), and mergewatch does not special-case either, so both kinds are inert to consumers and the dispatch outcome is byte-identical to today. They are named kinds (not collapsed into `Unrecognized`) solely so `IsUnrecognized()` is false for them and the section 2 diagnostic does not fire on routine behind/draft PRs. Adding a consumer predicate for either (e.g. `IsBehind()`) is deferred until a consumer actually needs to branch on it; the kind itself is added now because the diagnostic already needs to distinguish known fall-through from genuinely unseen vocabulary.

### 2. Gateway parse site — `internal/infra/github/gateway.go`

- `PullRequestDetail.MergeableState` changes type from `string` to `MergeabilityState`. The two assignment sites call `ParseMergeabilityState(...)` instead of storing the raw string, and case normalization moves out of the consumers and into the parser:
  - `gateway.go:1686` (`pullRequestDetailFromViewRow`, the GraphQL-shaped `gh pr view --json` view). **This site must also change which field it reads**: today it reads `row["mergeable_state"]`, but the GraphQL-shaped field lists (`prViewMetadataJSONFields`/`prViewFixerJSONFields`/`prViewReviewerJSONFields`/`prViewGatekeeperJSONFields` at `gateway.go:36-41`) request `mergeStateStatus`, not `mergeable_state`, so `row["mergeable_state"]` is always empty here and `ParseMergeabilityState` would parse an empty string regardless of input. The site reads `row["mergeStateStatus"]` (uppercase GraphQL vocabulary) and passes that to `ParseMergeabilityState`; the parser's lowercase step is what makes the uppercase GraphQL boundary reachable and tested.
  - **This field-source correction is a deliberate, scoped behavior change to durable data, not a no-op.** Today `row["mergeable_state"]` is absent on this path, so every snapshot captured through `CapturePullRequestSnapshot` (which persists this same GraphQL-shaped `PullRequestDetail` into durable `PayloadJSON` at `gateway.go:3189,3217`) stores an empty `MergeableState`. Reading `mergeStateStatus` and marshaling its `Normalized()` value changes that persisted field from `""` to the real provider value (e.g. `"dirty"`). This is intentional — the prior always-empty value was a latent read-the-wrong-key bug, not a contract anyone depends on — but it is *not* byte-identical persistence. The "consumer dispatch unchanged" scope therefore covers the Gatekeeper reason mapping and mergewatch action mapping (unchanged) and the `Evidence`/eventlog boundary (still `Normalized()`, byte-identical), **not** this durable snapshot field. The change is pinned by a regression test that drives a mixed-case `mergeStateStatus` through `pullRequestDetailFromViewRow` and asserts the stored `PayloadJSON` carries the normalized value (see Validation); reverting the field read to `mergeable_state` fails that test.
  - `gateway.go:1731` (`firstNonEmpty(row["mergeable_state"], row["mergeStateStatus"])` for the REST `ViewPullRequestMergeWatch` used by both Gatekeeper and mergewatch) wraps the existing `firstNonEmpty(...)` expression in `ParseMergeabilityState(...)`. This site already collapses both casings, so only the parse wrapping changes.
- `HasConflicts` (`:803,839,1680`) is left untouched — it is a separate GraphQL-only boolean, not a mergeability-state consumer.
- **Unrecognized-state diagnostic:** both parse call sites (`:1686` and `:1731`) emit a structured warning log when the parsed `MergeabilityState.IsUnrecognized()` is true, carrying `state.Raw()`. This preserves the existing action mapping (no error, no early return — the value still falls through to `ReasonMergeabilityNotClean` / check-pending) but makes a newly observed provider value observable in daemon logs the first time it appears. The diagnostic is required because the mergewatch snapshot disappears after `Classify` and `Raw()` is in-memory only, so without this log an unrecognized value is silent — classifying a kind is not by itself an observable signal. Because `behind` and `draft` are their own recognized fall-through kinds (section 1) with `IsUnrecognized()` false, the diagnostic fires **only** for a genuinely unseen value (the parser `default` arm) and stays silent for routine behind/draft PRs — these paths are hit repeatedly by PR views and mergewatch polling, so without the kind split the warning would fire on every gateway read of a behind/draft PR and write misleading entries suggesting new vocabulary was observed when it was not.
  - **Warning sink on `github.Options`/`Gateway`.** The current `github.Options`/`Gateway` has no general warning sink (only the narrow `ReviewSubmitDiagnostic func(event string, fields map[string]any)` for review-submit events). Add a `Warn func(message string, fields map[string]any)` field to `github.Options` — its signature matches `bootstrap.Logger.Warn` (`internal/bootstrap/logger.go:30`) — stored on `Gateway` as `warn` and emitted through a nil-guarded `g.emitWarn(message, fields)` helper, mirroring the existing `emitReviewSubmitDiagnostic` pattern (`gateway.go:2219-2222`). The parse call sites call `g.emitWarn("github.mergeable_state.unrecognized", map[string]any{"raw": state.Raw(), "site": "<1686|1731>"})` only when `state.IsUnrecognized()`. A nil `Warn` (e.g. a unit test that does not care) is a no-op, exactly like a nil `ReviewSubmitDiagnostic`.
  - **Runtime wiring at `internal/runtime/runtime.go:957`.** The production gateway construction `githubinfra.New(githubinfra.Options{GHPath: ..., Env: ..., Now: r.now, DiscoveryCacheTTL: ...})` currently supplies no diagnostic callback, so without this change a real daemon emits nothing and a gateway unit test injecting an ad hoc sink passes while production is silent. The construction is extended to forward the runtime's `bootstrap.Logger` through a nil-guarded closure — `Warn: func(message string, fields map[string]any) { if r.logger != nil { r.logger.Warn(message, fields) } }` — rather than the method value `r.logger.Warn` directly, so the unrecognized-state warning reaches `looperd.log` in production. The nil guard is required because `Runtime` is a supported construction context without a logger: `New` stores `options.Logger` unchanged at `runtime.go:319`, and `internal/runtime/detect_project_repo_test.go:67-68` starts a runtime via `New(Options{Config: cfg})` with no `Logger`, so binding the method value `r.logger.Warn` would evaluate `r.logger.Warn` on a nil `*logger` and panic before the gateway is created. The closure captures `r.logger` by reference and guards the call site, mirroring the nil-`Warn` no-op contract on `github.Options`/`Gateway`; the wiring does not introduce a new lifecycle dependency, only forwards an already-available sink when one exists.
  - **Integration coverage of the wiring, not just the sink.** A gateway unit test that injects a capturing `Warn` and asserts the warning fires for an unrecognized input (and not for known values) is necessary but not sufficient — it does not exercise the production construction. Add an integration test in `internal/runtime` (or a construction test in `internal/infra/github` that calls the same `Options` literal the runtime builds) that asserts the gateway built by the runtime's `Options` carries a non-nil `Warn` wired to the runtime logger, so a regression that drops the `Warn` closure from `runtime.go:957` fails the test. Because the wiring is a nil-guarded closure (not the method value `r.logger.Warn`), the same construction regression must also cover the nil-logger startup path: assert that `New(Options{Config: cfg})` with no `Logger` — the same shape `internal/runtime/detect_project_repo_test.go:67-68` uses — reaches gateway construction without panicking and yields a `Gateway` whose `Warn` is a non-nil no-op (calling it with an unrecognized input emits nothing and does not panic), so a regression that re-binds `r.logger.Warn` directly fails the test. This is the contract that makes "the parse sites emit a warning" honest in a real daemon rather than only under a test sink (see Validation).

### 3. Gatekeeper — `internal/gatekeeper/runner.go`

- `Evidence.MergeableState` stays `string` for durable audit reads; it is populated from `state.Normalized()` (i.e. `strings.ToLower(strings.TrimSpace(raw))`), **not** `state.Raw()`, so the persisted report is byte-identical to today's `report.Evidence.MergeableState = strings.ToLower(strings.TrimSpace(mergeability.MergeableState))` (`runner.go:337`). `Raw()` preserves the original provider string (e.g. an uppercase GraphQL `DIRTY` or whitespace-bearing fixture value) for in-memory telemetry/audit only; persisting `Raw()` into `Evidence` would change both the durable event value and the reason subjects for uppercase/whitespace inputs, which is not a byte-identical migration.
- The `:336-347` block becomes predicate calls on the parsed state:
  - `Mergeable == nil || state.IsEmpty() || state.IsUnknown()` → `ReasonProviderStateAmbiguous` (today's `state == "" || state == "unknown"`; `""` maps to `Empty` and `"unknown"` maps to `Unknown` in the parser, so `IsEmpty() || IsUnknown()` is the exact typed translation of the two-string check). `Mergeable == nil` stays a separate check at the consumer, exactly as today.
  - `!*Mergeable || state.HasConflict()` → `ReasonMergeConflict`.
  - `state.IsAmbiguousPolicyState()` → `ReasonProviderStateAmbiguous` with `Subject: "mergeability:" + state.Normalized()` (today's subject uses the normalized `Evidence.MergeableState`, so `Normalized()` keeps it byte-identical).
  - `!state.IsClean()` (the remaining fall-through, covering `Unrecognized` — a genuinely unseen value — plus the recognized fall-through kinds `Behind`/`Draft`, and any future non-clean kind that has no predicate) → `ReasonMergeabilityNotClean` with `Subject: state.Normalized()` (today's `:346` subject is the normalized `Evidence.MergeableState`). `Behind`/`Draft` reach this arm exactly as today's `behind`/`draft` strings did; only the diagnostic differs (silent for them, loud for `Unrecognized`).
- `providerPolicyStateIsAmbiguous` (`:643-650`) is deleted — its logic moves into `MergeabilityState.IsAmbiguousPolicyState()`.

### 4. mergewatch — `internal/coordinator/mergewatch/mergewatch.go` + `mergewatch_runner.go`

- `PRSnapshot.MergeableState` changes type from `string` to `MergeabilityState`. The snapshot builders in `mergewatch_runner.go` (`:184` full snapshot, `:253` partial snapshot) **copy `detail.MergeableState` directly into the snapshot** — they do **not** call `ParseMergeabilityState(...)` again. `PullRequestDetail.MergeableState` is already a parsed `MergeabilityState` after the gateway step (section 2), so re-parsing is unimplementable (`ParseMergeabilityState` takes a string) and would violate the parse-once invariant. The local `strings.ToLower(strings.TrimSpace(detail.MergeableState))` at `:184` and `:253` is deleted; the `mergeableState` local at `:184` becomes the typed `detail.MergeableState`. The `:205,216` comparisons (inside the check-run/status loops, which execute **before** the `PRSnapshot` return literal is constructed) switch to `detail.MergeableState.IsUnstable()` — the typed local in scope at those sites — **not** `snapshot.MergeableState.IsUnstable()`, because no `snapshot` variable exists while the loops run (the `PRSnapshot` is only built in the `return` literal at `:226` after the loops). `snapshot.MergeableState.IsUnstable()` would be an undefined-identifier compile error.
- `Classify` (`mergewatch.go:73`) switches to predicates:
  - `snapshot.Mergeable == nil || snapshot.MergeableState.IsUnknown()` → `ActionIndeterminate` / deadline path (`:90`). `IsUnknown()` is true **only** for the explicit `MergeabilityUnknown` kind (`"unknown"`), **not** for `MergeabilityEmpty` (`""`). This preserves today's exact behavior: mergewatch's current check is `snapshot.Mergeable == nil || snapshot.MergeableState == "unknown"`, which does **not** match the empty string, so an empty `MergeableState` with a non-nil `Mergeable` falls through to the normal check/pending classification (and eventually `ActionStillPending` / `ActionBranchProtectionChanged` for missing checks) rather than entering the indeterminate timer. Routing `""` through `IsUnknown()` was the first draft and is rejected here: it would change mergewatch for the empty + non-nil `Mergeable` case (entering the indeterminate/deadline path and eventually reporting `ActionBranchProtectionChanged`), and the assertion that empty always co-occurs with a nil `Mergeable` is not enforced — the REST/GraphQL decoders produce an empty `mergeable_state` independently of `mergeable`. Keeping `Empty` and `Unknown` as separate kinds (section 1) is what lets `IsUnknown()` mean exactly `"unknown"` here. `Mergeable == nil` stays a separate check.
  - `snapshot.MergeableState.HasConflict()` → `ActionConflict` (`:102`).
  - The `mergeableState == "unstable"` gating of failed-check detection (`mergewatch_runner.go:205,216`) becomes `detail.MergeableState.IsUnstable()` (the typed local in scope at those loop sites — see above). This is the one place a consumer needs the specific kind rather than a coarse predicate, because `unstable` is the signal that a failing required check is a *red-CI* failure rather than a missing one. The predicate is named for the intent the consumer already has.
- The `ActionStillPending` path (`:29` test case uses `"blocked"`) is unchanged: `blocked` is not conflict, not unknown, not unstable-failed-checks, so it falls through to `StillPending` exactly as today. Any `Unrecognized` value (a genuinely unseen string), the recognized fall-through kinds `Behind`/`Draft`, and `Empty` with a non-nil `Mergeable` fall through the same way — preserving today's behavior for unmatched, behind/draft, and empty strings.

### 5. Exhaustiveness

The parser's switch is exhaustive over the known vocabulary with a `default` → `MergeabilityUnrecognized`. A genuinely new GitHub state (e.g. a future `"pending"`) lands in `Unrecognized`, preserves its original string via `Raw()`, and falls through with the existing behavior, rather than silently matching neither consumer's subset. The routine `behind`/`draft` values land in their own recognized fall-through kinds (`Behind`/`Draft`), not `Unrecognized`, so they fall through identically but do **not** trip the diagnostic. Because the mergewatch snapshot disappears after `Classify` and `Raw()` is in-memory only, classifying a kind by itself is not an observable signal — so the gateway parse call sites (section 2) emit a structured warning through the `Warn` sink wired on `github.Options`/`Gateway` and forwarded from the runtime logger at `runtime.go:957`, when the parsed state `IsUnrecognized()` (true only for the `default` arm, not for `Behind`/`Draft`), carrying `state.Raw()`, while preserving the existing action mapping (no error, no early return, no behavior change). This is the "fails loudly in one place" property made honest: the parser is the single site that decides kind, the warning makes a genuinely unseen provider value observable in daemon logs the first time it appears (rather than silently falling through two consumers whose snapshot is gone, or noisily firing on every routine behind/draft PR), and the regression table asserts every known string maps to the right kind plus that an unrecognized input fires the warning through the production-wired sink while `behind`/`draft` do not.

Go does **not** require enum-like switches to cover every constant, so adding a `MergeabilityKind` does **not** by itself produce a compile-time signal in the parser or consumers — and the consumers here call coarse predicates (`IsClean`/`HasConflict`/`IsAmbiguousPolicyState`/`IsEmpty`/`IsUnknown`/`IsUnstable`/`IsUnrecognized`), not a `switch` over the kind, so the compiler cannot flag a new kind that no predicate covers. The "compile-time enforcement" claim is therefore **not** made for this design. Exhaustiveness is enforced by an explicit, mechanically-bounded test mechanism instead:

- `internal/infra/github/mergeability_test.go` includes an **exhaustiveness table** whose iteration is **mechanically bounded by the enum itself**, not a hand-maintained slice. The constant block ends with a `mergeabilityKindCount` sentinel (the last `iota`), and the test loops `for kind := MergeabilityEmpty; kind < mergeabilityKindCount; kind++`, asserting for each kind: (a) the predicate behavior is defined — `IsClean`/`HasConflict`/`IsAmbiguousPolicyState`/`IsEmpty`/`IsUnknown`/`IsUnstable`/`IsUnrecognized` each return the intended bool — and (b) at least one parser input maps to it. Because the range is derived from the sentinel, inserting a new `MergeabilityKind` constant **above** `mergeabilityKindCount` automatically extends the iterated range — the new kind is visited and asserted with no second edit. A hand-maintained `var allKinds = []MergeabilityKind{...}` slice is deliberately **not** used: adding a kind without adding it to such a slice leaves the test iterating the same old entries and passing, which is exactly the silent-drop failure this check exists to catch. The sentinel-bounded loop makes the cardinality a property of the enum, so the only way to add a kind and keep the test green is to also give it a parser input and defined predicate behavior. A `go vet`/staticcheck run does not replace this; it is a deliberate, code-owned check.
- The "no string literals remain" grep in Validation is the backstop that prevents a consumer from re-introducing a local string compare that bypasses the predicates entirely.

This is an explicit, test-owned exhaustiveness mechanism, not compiler-enforced. The trade-off is that a contributor who adds a kind and updates the table but forgets a consumer predicate will not get a compile error — the regression tables for Gatekeeper and mergewatch (below) are what catch a missed consumer mapping.

## Risks

- **Predicate semantics drift from string semantics.** The risk of a typed refactor is that the predicate boundaries redraw the lines the strings drew. Mitigation: the predicate set is derived *exactly* from the current string comparisons — `IsAmbiguousPolicyState()` is precisely `{"blocked","unstable","has_hooks"}`, `HasConflict()` is precisely `{"dirty"}`, `IsEmpty()` is precisely `{""}`, `IsUnknown()` is precisely `{"unknown"}` (the explicit provider-unknown only), `IsUnrecognized()` is precisely the parser `default` set (a genuinely unseen non-empty, non-`"unknown"` value not in the known set — **not** `behind`/`draft`, which have their own `Behind`/`Draft` kinds), and `Empty`/`Behind`/`Draft`/`Unrecognized` deliberately match no consumer predicate besides `!IsClean()` (and `IsEmpty()` for `Empty`) so they keep the old fall-through. The two consumers' different treatment of `""` is preserved by splitting `Empty` and `Unknown` into separate kinds rather than collapsing them into one `IsUnknown()`. The regression tests (below) pin the mapping for every state both consumers currently handle, so any redraw fails the test.
- **Case/casing regression.** Today each consumer lowercases; the parser must lowercase too, or an uppercase GraphQL `mergeStateStatus` (now actually read at `gateway.go:1686` per section 2) reaches consumers un-normalized. Mitigation: `ParseMergeabilityState` lowercases; the parser test includes uppercase inputs, including the uppercase GraphQL vocabulary read at the `:1686` site.
- **`behind`/`draft` diagnostic noise (the failure this design avoids).** `behind` and `draft` are routine, documented provider states for ordinary PRs (behind base, draft). The first draft collapsed them into `Unrecognized`, which made `IsUnrecognized()` true for them and caused the section 2 diagnostic to fire on every gateway read of a behind/draft PR — PR views and mergewatch polling hit these paths repeatedly, with no deduplication, so ordinary PR states continually wrote misleading warning entries suggesting new vocabulary was observed. This design instead gives them their own recognized fall-through kinds `Behind`/`Draft` (no consumer predicate besides `!IsClean()`, `IsUnrecognized()` false), so consumer dispatch is byte-identical to today's fall-through while the diagnostic fires only for the parser `default` arm (a genuinely unseen value). The trade-off versus collapsing them is two extra exhaustiveness-table rows; the consumer-relevant distinction that justifies the kinds is the diagnostic boundary itself — the warning must not conflate "GitHub returned a value we have documented and expect" with "GitHub returned a value nobody has seen before." Adding a consumer *predicate* for `Behind`/`Draft` (e.g. `IsBehind()`) is deferred until a consumer actually needs to branch on either; the kind exists now because the diagnostic already needs to distinguish them.
- **Diagnostic-sink wiring regression.** The unrecognized-state warning reaches daemon logs only if `github.Options.Warn` is wired to the runtime logger at `runtime.go:957`. A gateway unit test injecting an ad hoc `Warn` sink passes while production stays silent if the runtime construction drops the `Warn` closure. Mitigation: an integration/construction test asserts the gateway built by the runtime's `Options` carries a non-nil `Warn` forwarded from `r.logger`, so dropping the wiring fails the test (see section 2 and Validation). The wiring is a nil-guarded closure (not the method value `r.logger.Warn`) precisely because `Runtime` is constructible without a logger (`New(Options{Config: cfg})` at `internal/runtime/detect_project_repo_test.go:67-68`); binding the method value directly would panic at gateway construction on that path, so the same construction regression also covers the nil-logger startup case.
- **Persisted-format compatibility.** `Evidence.MergeableState` is a durable event field. Keeping it `string` and populating it from `state.Normalized()` (not `Raw()`) means existing eventlog readers see byte-identical values — `Normalized()` is exactly today's `strings.ToLower(strings.TrimSpace(...))`. `Raw()` is in-memory telemetry/audit only. The type also crosses the `CapturePullRequestSnapshot` `PayloadJSON` boundary (the whole `PullRequestDetail` is marshaled there); `MarshalJSON` emits `Normalized()` so the stored snapshot keeps `"MergeableState":"<normalized string>"` rather than the `"MergeableState":{}` an unexported-field struct would produce — preserving the persisted *schema*, covered by a stored-snapshot regression test (below). The persisted *value* on the GraphQL view path does change from `""` to the real normalized value, because the section 2 field-source fix corrects a latent always-empty read; that is the one intentional non-byte-identical effect and is pinned by its own regression test (below), separate from the `MarshalJSON` schema test.

## Out of scope / future

Any future consumer that needs to branch on a mergeability state extends this typed switch instead of adding a third string-compare site. When it adds a predicate, the parser's exhaustiveness and the regression tables are the surface that grows — by design, in one file.
